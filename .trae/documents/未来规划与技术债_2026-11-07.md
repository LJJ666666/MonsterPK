## 0. 使用规则（防止烂尾）

1. 每条规划必须有 **ID / 来源 / 产品口径 / 当前现状 / 偿还缺口 / 偿还阶段 / 是否阻塞**。
2. **登记 ≠ 已实现**：状态只允许 `📋 待设计` / `🔨 进行中` / `✅ 已偿还`。
3. 每个 P4-2 阶段开工前由 tx 核对本台账，判断是否有必须先偿还的前置项；**不因此阻塞当前阶段的，明确写「不阻塞」**。
4. 偿还时必须同步改本表状态、任务表时间线、规范 / bug_log（若涉及）、`scripts/doc_check.py` 断言，并在 commit 末尾写验收数字。
5. 台账条目由 `scripts/doc_check.py` 硬校验存在性，防止文档被误删或悄悄改口径。

## 2. 详细条目

### F01 榜单周期结算 — 📋 待设计

- **来源**：杰哥 2026-11-07「周期结算、榜单奖励会有，记录好未来再设计」。
- **产品口径**：榜单不是永久累计，按周期结算（日 / 周 / 赛季待定）；结算时点、是否分组、跨周期累计规则待定。
- **当前现状**：P4-2a 四榜是**实时派生**、TTL=0 的只读读模型（`GET /api/rank/:type` 每次从 `Save` 落库真值算），无周期、无快照、无结算任务。榜单类型注册表已预留，加周期不改协议。
- **偿还缺口**：周期定义与服务端配置、结算任务（幂等、可重跑）、周期快照表或 append-only 事件、历史榜查询、时区口径。
- **不冲突点**：换周期快照时接口与前端零改动（P4-2a 已把读模型收口在 `modules/rank.ts`）。

### F02 榜单奖励 — 📋 待设计

- **来源**：同 F01。
- **产品口径**：有榜单奖励，具体名次 / 奖励内容 / 发放方式待定。
- **当前现状**：P4-2a 明确不做奖励；榜单只读、无写入口。
- **偿还缺口**：奖励表（内容表派生）、结算后发放（**必须服务端写档，经 `commitState()`，客户端不得上报领取**）、防重复领取（复用 nonce / 幂等键）、与 CAS `revision` 的交互。
- **依赖**：先还 F01，奖励才有结算时点。

### F03 单机隔离版（管理员自测） — 📋 待设计

- **来源**：杰哥 2026-11-07「管理员测试菜单能造满属性，放进全服榜会污染数据，后续会做一个隔离版本（单机版）自测就好，那就不会污染了，**现在先不用纠结管理员的问题**」。
- **产品口径**：未来出一个隔离的单机自测版本，管理员造数据只在隔离环境里跑，不进入线上全服真值。
- **当前现状**：P4-2a 已把**封号账号与管理员账号**从榜单派生中排除（`modules/rank.ts`）。杰哥明确**不再为此投入**，该排除逻辑保留为兜底即可，不删不改、不额外做隔离逻辑。
- **偿还缺口**：单机隔离版的环境与数据边界；隔离版与线上共用代码时如何保证真值不互通。
- **边界**：**本轮不做任何改动**，也不新建"管理员白名单 / 标记"之类机制。

### F04 召唤师等级：口径修正（重要） — 📋 待设计

- **来源**：杰哥 2026-11-07「召唤师等级我的初衷是，**人物的等级，跟宠物最高等级挂钩的那种。等于账号的等级**。我 10 级那么我宠物最高也只能升级到 10 级（未来可能重新设计，可能会是 N+5 级之类的想法）」。
- **产品定义（钉死，不是待定）**：
  - 召唤师等级 = **人物 / 账号等级**，是账号级真值，**不是宠物属性、不是进度派生值**。
  - **与宠物等级上限挂钩**：账号 `L` 级 → 宠物等级上限 `L`（未来可能改成 `L + 5` 之类的 N+5 规则，**规则可变，但「账号等级决定宠物等级帽」这层关系不变**）。
  - 等级帽由**服务端强制**：升级、经验结算、进化、捕获初始化等所有会改宠物等级的入口都要校验，客户端上报等级一律无效。
- **当前现状（明确标为占位偏差）**：P4-2a 实现的是**派生占位公式** `1 + 首通区域数×2 + floor(队伍等级总和/10) + 图鉴已捕获物种数`（上限 9999），见 `backend/src/game/rank.ts`。它是为了避免在四个榜单都暂定时锁死存档结构而做的临时口径，**不符合上面的产品定义**，不能当作已实现。
- **偿还缺口**：
  1. `SaveData` 增 `playerLevel`（及可能的经验值）→ **必须联动** `src/game/saveVersion.ts::SCHEMA_VERSION`、`backend/src/lib/saveValidator.ts::EXPECTED_SAVE_VERSION`、migrate 分支三处；老存档要能玩。
  2. 账号经验 / 升级规则、等级帽常量（`levelCap = playerLevel` 或 `+N` 配置化，**服务端可调**）。
  3. 所有宠物等级写入口加等级帽校验与单测。
  4. 榜单 `summoner_level` 改读真值，删掉派生占位公式。
  5. UI 文案去掉「派生」说明。
- **偿还阶段**：独立子项，建议排在 P4-2c 之前或与剧情系统合并；**不阻塞 P4-2b 房间内核**（房间层不读召唤师等级）。
- **纪律**：在此之前，任何文档 / UI 不得声称「召唤师等级已实现」；契约 §4 与后端 `RANK_META` 描述已加「占位」字样。

### F05 战力公式数值 — 📋 待设计

- **来源**：杰哥「战力公式可先待定（有这个榜单，和这个规划就好）……按照宠物的总属性六维来计算……不代表更强」。
- **已钉死**：单宠 = 有效六维之和（`maxHp + atk + def + spAtk + spDef + spd`，**用 `maxHp` 不用 `hp`**）；全队 = `party` 之和；不代表实战强弱、不参与匹配 / 伤害 / 奖励 / 解锁任何判定。
- **待定**：系数、权重、取整、等级修正。当前 `game/power.ts` 简单求和占位，换公式只改这一个纯函数。

### F06 宠物装备 — 📋 待设计

- **来源**：杰哥「后续应该会出宠物装备，那样也会加攻击力或者一些属性来影响这只宠物的总战力」。
- **已钉死**：加成是**服务端独立真值**，叠加成 `effectiveStats = 基础面板 + 装备加成`，**不写回 `MonsterInstance` 面板**（避免污染 `digestOf` / authority 摘要与 CAS 风控）；装备上线时 `game/power.ts` 零改动。
- **待定**：装备槽位、加成数值、获取与强化、装备本身是否进存档结构（若进，走 F04 同款迁移纪律）。
