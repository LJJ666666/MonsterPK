## mobile-server 部署推进（承接，root 已开）
- 杰哥在雷电开了 root（`su -c id`=uid0），bootstrap 已完成转正，Termux 原生包路线跑通（**放弃 proot**：Termux 源有原生 PG18/Redis8/Node24，x86_64 免 glibc 兼容层）。`deploy-native.sh` 装三件套→initdb→起 PG/Redis 全部成功。
- **踩坑1（apt 半装状态）**：bootstrap 后 73 包停在旧版，node24 链接报 `cannot locate symbol _ZNSt6__ndk113__hash_memoryEPKvm`（libc++ 27c 旧 so 缺符号）→ `apt-get reinstall libc++` 升到 30 修好；又报 `OSSL_PROVIDER_add_conf_parameter`（openssl 3.4.1 vs node 需 3.6.5）→ 病根是 apt 中断半装，**正解一次性 `apt-get upgrade -y`（67 包）让依赖自洽**，别逐个补符号。
- **踩坑2（纯 Node 打 tar 校验和错）**：`pack-backend.mjs` 的 ustar header checksum 只置 `h[148]='0'`、其余留 0 → 标准 tar 全报 `bad checksum/host not a tar archive`。**正确做法：148..155 先 `fill(0x20)` 8 个空格再逐字节求和，写回 6 位八进制+NUL+空格**。已修并用 Python tarfile 验证 122 文件可解。
- **踩坑3（/sdcard 映射不同步）**：adb push 到 `/sdcard/mpk/` 不会同步进 Termux 私有视角 `$HOME/storage/shared/mpk/`（md5 不同、读到旧包）。修法：`adb push` 到 `/data/local/tmp/` → root `cp` 到 Termux 私有目录 + chown u0_a75/chmod 666。
- **踩坑4（bash 层层转义）**：adb shell 里内嵌 `$PATH`/`$()` 会被宿主机 Bash 提前展开成 Windows PATH 导致语法错。正解：脚本 Write 落盘 → adb push → `run-as com.termux <termux-bash> -s < /sdcard/mpk/x.sh` stdin 喂入。`/sdcard` noexec，不能直接 `bash /sdcard/x.sh`（exit 126）。
- 状态：apt 全量 upgrade 完成（67 包），node v24.22.3 + OSSL 符号齐全；deploy-native.sh 已跑通到 npm install（95 包 + approve scripts + rebuild 全部成功）。
- **部署链已清的坑（按顺序）**：① apt cache 被 root 污染 → root 删 cache；② tar checksum bug（见上）；③ `/sdcard` 不同步 → root cp 到 Termux 私有目录；④ npm12 `EALLOWREMOTE` → `NPM_CONFIG_ALLOW_REMOTE=all`；⑤ npm12 allowScripts 挡 prisma/esbuild → `npm install-scripts approve --all` + `npm rebuild`；⑥ Android 无 `/usr/bin/env` → .bin 符号链接不能直接跑，用 `node <真实JS入口>`（prisma=node_modules/prisma/build/index.js，tsx=dist/cli.mjs）；⑦ npx12 在 Termux 解析本地 bin 失常 → 弃 npx 直接 node 入口。
- **⚠️ 决定性死胡同（勿再试）**：Prisma 5.x 的 engine 是 **glibc 二进制**——3.0.x 版 `readelf -d` 依赖 `libc.so.6`/`ld-linux-x86-64.so.2`/`libm.so.6`/`libpthread.so.0`，Android bionic 根本没有；1.1.x 版则缺 `libssl.so.1.1`。**Prisma engine 无法在 Termux 原生 bionic 上跑**。已做：schema 改 `binaryTargets=["debian-openssl-3.0.x"]`、3.0 query engine 下载成功、设 `PRISMA_QUERY_ENGINE_LIBRARY` 仍 dlopen 失败。→ **正解=回到原 PLAN 的 proot Debian（真 glibc）**，或换真机 arm64（但 Prisma engine 仍要 glibc，真机也需 proot/termux glibc 环境）。原生包路线在此止步，别再跟 engine 兼容搏斗。
