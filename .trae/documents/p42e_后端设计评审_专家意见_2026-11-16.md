## 1. 结论摘要

1. **设计在当前形态下「至多一次被接受」成立，但「全局只接受一次」不成立**：`seenNonces` 是 `Room.data` 整包 JSON 里的一个普通数组（`roomRegistry.ts:117` 类型、`390` 初始化、`569-570` 写入），只保留最近 64 条（`MAX_SEEN_NONCES=64`，`roomRegistry.ts:170`）。窗口外重放会被当成合法首提。
2. **最大单点风险不是并发窗口，而是「去重依据与房间整包状态同生共死」**：任何绕过 `revision CAS` 前提的整包覆盖写，都会把去重记录一起冲掉。目前 CAS 挡住了这条路径（`pgRoomStorage.ts:68-79`），所以是**结构性脆弱**，不是当前已失效。
3. **本次偶发红的直接根因不在产品代码，在测试断言**：旧断言把「哪一路该输」写死成 `rb`，而并发语义只保证「恰好一路赢」。同一仓库里 `e2e_multi_instance.mjs:283-286` 早就是正确写法（`okCount===1 && replayCount===1`），p42e 是唯一的例外。
4. 设计稿列了 C1/C2/C3/C4 四个候选根因（设计稿 §3），**恰好漏掉了可能性最高的 C0：断言假定了并发顺序**。建议补进复现方案，避免后续按错误定因去改产品。
5. 真要动产品，优先级应是「唯一约束表 > 拒绝路径也烧 nonce > 事务内重试改 savepoint > `normalizeRoom` 补字段」；**但这些都不该和本次红灯混在一个工单里**。

## 2. 设计层面

### 2.1 `seenNonces` + revision CAS 能否保证「同一 nonce 全局只被接受一次」

先固定事实链（均已核对源码）：

- 判重是纯内存数组 `includes`：`roomRegistry.ts:565`。
- 写入与 64 淘汰：`roomRegistry.ts:569-570`。
- 写回是行版本 CAS：`pgRoomStorage.ts:68-79`（`updateMany({where:{roomId, revision: base}})`，`base = room.revision - 1`）。
- CAS 失败抛 `RoomCasConflictError`（`roomRegistry.ts:316`），`retryCas` 整段重跑最多 5 次（`roomRegistry.ts:784-793`）。
- 房间 action 全段在 `withRoomUnit` 内（`room.ts:294`），= `withRoomLock(roomId)` + 同一 PG 事务（`roomUnitOfWork.ts:92-94`）。

分场景严格推理：

| 场景 | 结论 | 推理 |
|---|---|---|
| **同实例并发** | 成立 | 进程内锁是 Promise 链严格串行（`lockProvider.ts:29-41`）；即使生产换 Redis 锁，同一 key 也只有一个持有者（`redisLockProvider.ts:131-141`）。两路请求在 `withRoomUnit` 处被排队，后到者 `get` 时前者已提交。 |
| **跨实例并发** | 成立 | Redis 锁只压冲突概率，真正裁决是 CAS。两事务都读 `revision=N`：胜者写 `N+1`；败者 `count=0` → 抛错 → `retryCas` 重跑 → READ COMMITTED 下重读到胜者已提交的 `seenNonces` → 409。**不存在两个事务都写成功**。 |
| **读到旧副本** | 成立 | 旧副本的 `revision` 已被抬走，`set` 必然 0 行。`writeBack` 不改 revision（`pgRoomStorage.ts:89-95`），但它能成功的前提是「该 revision 未被 bump」，因此不可能把「已含 nonce 的 N+1」写回成 N。 |
| **事务回滚** | 成立（语义上正确） | nonce 与房间同事务回滚 = 这次提交从未发生。客户端拿 5xx、重试同 nonce 会成为「合法首提」——这正是幂等该有的行为，**不能算缺陷**。 |
| **64 条上限淘汰** | **不成立** | 见下方专项。 |
| **房间重建** | 成立（但靠 id 兜底） | 路由侧 roomId 一律 `randomUUID()`（`room.ts:244`），删除后重建不可能复用 id；`create` 虽允许外部传 roomId（`roomRegistry.ts:353`），目前无调用方这么做。 |

**64 窗口是真实缺陷，不是理论风险**：6 人 coop，一回合最多消耗 6 个 nonce，约 10 个回合后最早的 nonce 就被 `shift()` 挤掉（`roomRegistry.ts:570`）。此时重放该 nonce：

- `seenNonces.includes` → 不命中（已被淘汰）；
- `submitted.includes(seat)` → 通常也不命中（`advanceTurn` 在 `roomRegistry.ts:626-627` 已清空）；
- 于是**直接走进正常提交分支并 200**，意图被当成新回合的合法输入。

触发场景很日常：客户端离线队列里压着一条十几回合前的请求，重连后补发。所以设计稿 F4「seenNonces 只增不减、回合推进不清空」这句是对的，但「不清空」≠「永久保留」。

**结论**：在「64 条窗口内 && 同房间生命周期内 && 单库」三个前提同时满足时，`seenNonces + CAS` 能给出 at-most-once；任一前提破掉就不成立。设计稿 §2 的 F3~F5 推理方向正确，但漏了窗口这一条，导致「只要落库了第二路就该 409」这个结论**只在窗口内成立**。

### 2.2 锁 / 事务 / CAS 的职责边界

三者职责在代码里是清晰的，但在文档和实现之间有一处**实质性偏差**：

- 锁 = 同 key 串行，降低 CAS 冲突、保证 `load → decide → write` 的读一致；
- 事务 = 原子性（`Room` + `RoomQuota` + `Save` + `CoopRewardGrant`，`roomUnitOfWork.ts:1-17`）；
- CAS = 最终裁决（`pgRoomStorage.ts:68-79`）。

**「锁 TTL 到期 → 两个事务并行」是可能的**，且不能靠注释排除：

- 租约 TTL 30s、watchdog 10s（`redisLockProvider.ts:25-27`），watchdog 是 `setInterval`（`146-157`）。事件循环被长任务（同步大 JSON 序列化、GC、CPU 打满）阻塞超过 30s，或 Redis 抖动导致续租失败，租约就会易主，两个持有者同时进入临界区。
- 一旦发生，**「双接受」仍被 CAS 挡住**，但**非幂等副作用不会被挡住**（见 2.3 与 3.6）。
- 另有 API 注释与实现不符：`lockBootstrap.ts:8-9` 声称「运行期 Redis 断连……写路径由 W2 的 DB 条件更新兜底」，实际 `acquireAndRun` 里 `backend.acquire` 抛错没有任何 catch（`redisLockProvider.ts:131-132`），请求会直接 500，**根本走不到 CAS**。兜底只对「租约过期」成立，对「Redis 报错」不成立。

**「锁内 await 事务超时」不会留下语义空窗**：Prisma 事务 `maxWait=5s / timeout=15s`（`roomUnitOfWork.ts:40-44`），超时 → 抛错 → 事务回滚 → `finally` 释放锁（`redisLockProvider.ts:163-172`），不存在半提交。但要注意下一条：

- **`maxWait` 排队失败（连接池打满）会让「先到的那一路直接 500」**，后到者于是成为合法首提 → 与本次现象**同形**。这是 C1 的一个具体、可检验的机制；是否命中要看服务端日志里有没有 Prisma `P2028`。**未取证**（本地 `DATABASE_URL` 未设 `connection_limit`，用 Prisma 默认，全量并行时是否耗尽我无法从源码判定）。

### 2.3 `retryCas` 5 次耗尽后的行为

- 耗尽 → `throw last`（`roomRegistry.ts:792`），`RoomCasConflictError` 一路冒泡出 `applyRoomIntent`；全仓 **没有任何 `setErrorHandler`**（`grep setErrorHandler|RoomCasConflict` 只命中定义处 `roomRegistry.ts:149/152/316/788`）→ Fastify 默认 **500 `Internal Server Error`**，无业务 `code`。
- **不会与 `INTENT_REPLAY` 混淆**：一个是 500 无 code，一个是 409 带 code（`room.ts:67`）。语义上没有撞车，但契约上有个洞：客户端拿不到可判定的业务码，WS 分支则完全静默（`realtime.ts:505-507` 只打日志，不回 error 帧）。
- 真正该记一笔的是：**`retryCas` 在同一个事务里重跑，失败尝试已执行的 SQL 不会回滚**。见 3.6，这是本次评审里唯一「会真正写坏数据」的点。

### 2.4 独立表 + `(roomId, nonce)` 唯一约束，是否真能消除这一类竞态

**能消除「64 窗口 + 整包覆盖脆弱性」这一类，但消除不了本次红灯**（本次是断言错，不是产品竞态）。设计稿把 A 方案和本次偶发红绑在同一条因果链上，这一步推理需要修正。

风险确实会转移，且四条都要在方案里写死，否则是「换个地方漏」：

1. **写放大 / 事务数量**：每条 intent 多一次 INSERT。coop 每个回合 ≤6 条，量级可接受。
2. **清理策略**：推荐 `Room` 删除时 `ON DELETE CASCADE`，让 nonce 生命周期严格跟房间 TTL 走。若改「固定 10 分钟窗口回收」，等于把「64 条窗口」换成「时间窗口」，**同一类漏洞原样保留**。
3. **房间删除后残留**：不带外键的 `(roomId, nonce)` 会在删房后永久堆积，必须级联或 sweep。
4. **幂等语义仍需单独决策**：唯一约束只解决「是否重复」，不解决「重复时回 409 还是回放首响应」（设计稿 §5 的 C 方案）。

补充一个设计稿 §7-1 的问题（去重键作用域）：**建议 `(roomId, nonce)`，但前提是把客户端 nonce 约束成全局唯一**（UUID/128bit）。当前 nonce 是客户端自选短串（测试用 `e2`），如果同一房间内两个座位各发一个 `e2`，后发者会被判 `INTENT_REPLAY` 而不是「自己那一路的合法提交」——**一个成员可以抢占另一个成员的 nonce**。若坚持短 nonce，就必须改成 `(roomId, seat, nonce)`；两者不能各取一半。

## 3. 实现 / 语法层面（发现即列）

### 3.1 `seenNonces` 的 64 条淘汰 —— 缺陷，不是「可接受窗口」
`roomRegistry.ts:170`（上限）、`569-570`（push + shift）、`539-540`（autopilot 同款）。理由见 2.1：淘汰后老 nonce 重放会**直接 200**，因为 `submitted` 也已被 `advanceTurn` 清空（`626-627`）。建议：淘汰条件与「最小可接受 turn」绑定（例如记 `nonceTurn`，早于 `turn - K` 的直接判重放），或迁到唯一表。

### 3.2 `validIntent` 对 nonce 的校验 —— 两套规则漂移
`roomRegistry.ts:174-177`：长度 ≤64、字符集 `[A-Za-z0-9_:\-]`、**允许冒号**。
REST 层 `room.ts:386` 的 nonce 正则**不含冒号**；`autopilotSchema` 同样不含（`room.ts:391`），但最终又落到允许冒号的 `validIntent`。同一字段在入口与内核两套规则，改动时极易一边过一边不过。另外**没有任何新鲜度/不可预测性校验**——nonce 由客户端全权决定，服务端只保证「同一字符串不重复」。这与 2.4 的跨座位抢占叠加，构成一个成员可干扰另一个成员重试的通道（严重度低，但真实）。

### 3.3 `loadAndMutate` 用 `JSON.stringify` 前后比较 —— 正确但有代价
`roomRegistry.ts:808`（before）、`813`（after）、`815`（不一致才 bump）。同一对象的键序稳定，所以判定语义正确。两个问题：
- **性能**：每次尝试对整房态做两遍 `stringify`。coop 房间含 6 房状态 + 双方队伍快照，量级 KB 起；`sweep` 每 250ms 遍历全部房间（`roomRegistry.ts:767-775`）时会成为 CPU 热点，而 CPU 紧张又正好会加剧 2.2 的租约续期风险 —— 两个问题会互相放大。
- **正确性**：这是「是否 bump」的唯一判据。`fn` 若改了又改回（净变更 0），会静默不落库；当前无此路径，但这是个隐形约束。建议换显式 `dirty` 标记。

### 3.4 `submitIntent` 的检查顺序 —— **顺序正确**，但有一处反向缺口
`roomRegistry.ts:565`（先判 `seenNonces`）→ `566-567`（再判 `submitted`）。
- 顺序**必须是这样**：否则「回合推进后重放旧 nonce」会先撞 `TURN_ALREADY_SUBMITTED`（新回合 `submitted` 是空的，不会撞，但同回合内会），拿不到 `INTENT_REPLAY`。`e2e_p42e_nonce_race.mjs:103-105` 正在验这个语义，写法是对的。
- 缺口在反面：被判 `TURN_ALREADY_SUBMITTED` 的 nonce **不会入 `seenNonces`**（`567` 在 `569` 之前 return）。于是同一个 nonce 下一回合重放会被接受 → 迟到的意图落到错误的回合。是「拒绝也烧 nonce」还是「明确不烧」，需要在文档里定死，不能停留在现状。

### 3.5 `withUserRooms`（不持房间锁、跨多房间写）不会冲掉 `seenNonces`，但会放大冲突
`roomRegistry.ts:826-839`，调用方是 `markDisconnected`（`456-474`）/`reconnect`（`481-502`），WS 断线路径**只套 `runInRoomUnit`、不套 `withRoomLock`**（`realtime.ts:528-531`）。
- 覆盖风险：不存在。旧的 revision 写不回（`pgRoomStorage.ts:68-79` 的 `where revision=base`），所以「拿旧副本冲掉新 `seenNonces`」在设计稿 C2 假设下**不成立**——这条可以放心排除。
- 真实代价：它和持锁写者产生 CAS 冲突，冲突恢复成本全压在 `submitIntent` 的 `retryCas` 上，而 `retryCas` 是在**事务内**重跑的（见 3.6）。所以 `markDisconnected` 是 3.6 的主要触发源之一。

### 3.6 **事务内重试会重复执行非幂等副作用**（本次评审发现的最实在的实现缺陷）
`retryCas` 包住的是整个 `load → mutate → bump`（`roomRegistry.ts:806-818`），而它运行在 `withRoomUnit` 打开的事务**内部**。CAS 失败只意味着 `updateMany` 影响 0 行，**事务本身没有回滚**；重试时前面已经执行的 SQL 全部生效过一次。

受影响路径：
- `advanceTurn → finishQuota(commit) → settleQuota`（`roomRegistry.ts:603/622` → `328-335` → `pgRoomStorage.ts:151-186`）：`RoomQuota.committed` 与 `RoomQuotaDaily.committed` 会被**多加一次**，直接吃掉玩家每日次数；`daily.updateMany({committed:{lt:limit}})` 的 `lt` 判断也会被这次多记影响。
- `abandon/settle → finishQuota(release)`：`release` 用 `GREATEST(held-1,0)`（`pgRoomStorage.ts:155`），**非幂等**，重试会多扣 `held`。
- 触发条件：租约失约（2.2）或与 `markDisconnected`（3.5）撞车。概率低，但后果是「静默多扣次数」，且没有任何日志能复盘。

建议：把 `retryCas` 挪到事务外层（每次重试重开事务），或在事务内用 savepoint；前者改动更小。

### 3.7 `offerAutopilot` 的 no-op 分支跳过去重
`roomRegistry.ts:534-535`：`target.autopilot === params.enabled` 时直接 `ok(room)`，**在 nonce 判定（`536-541`）之前**。所以这条 nonce 既不去重也不烧掉，且返回 200 但 revision 不变（`loadAndMutate` 的 `before===after` 不 bump，`815`）。语义上「已达成目标状态 = 幂等成功」说得通，但与 `submitIntent` 的「先判重放」不一致，后续改这块时容易踩。

### 3.8 `normalizeRoom` 不补 `seenNonces` 等数组字段
`roomNormalize.ts:24-35` 只补 `pvpSettled` / `coopSettled`。若读到字段引入之前的旧行（或反序列化异常），`room.seenNonces` 为 `undefined`，`roomRegistry.ts:565` 的 `.includes` 会抛 `TypeError` → 500。当前 `create` 必写（`390`），只在跨版本残留数据上触发，属低概率；但「补了两个可选布尔、漏了三个数组」本身是不一致，建议一并补。

### 3.9 状态码映射的隐式契约
`STATUS_BY_CODE`（`room.ts:56-72`）登记了 `INTENT_REPLAY: 409`（`67`）与 `TURN_ALREADY_SUBMITTED: 409`（`68`），但 `applyRoomIntent` 会返回的 `COOP_INTENT_INVALID`（`room.ts:299`）**没有登记**，靠 `statusFor` 的 fallback `?? 400`（`74-76`）落 400。测试断言 400 能过，但这是隐式契约，改动 `STATUS_BY_CODE` 时容易漏。

### 3.10 事务内多一次无谓读
`room.ts:297` 在 `submitIntent` 之外又 `rooms.get()` 一次，只为校验 coop intent。多一次往返、且与后面 `submitIntent` 内的 `get` 是两次读（同一事务，一致性没问题）。可合并，属优化项。

## 4. 对测试断言的评价

### 4.1 旧断言（原 `e2e_p42e_coop.mjs:145-146`）**不符合**并发语义
```js
suite.check('重复 nonce 被拒 409 INTENT_REPLAY',
  rb.status === 409 && rb.data?.code === 'INTENT_REPLAY', ...);
```
`Promise.all([ra, rb])` 的数组下标只承诺**发起顺序**，不承诺**到达顺序**。两条请求走 undici 的独立连接，服务端的房间锁又是「谁先到谁拿」——`redisLockProvider.ts:8-9` 甚至明写了「只保证不同时执行，不保证先到先得」。机器慢 / 全量并行时，后发起的 `rb` 完全可能先到服务端，于是 `rb` 成为胜者拿 200、`ra` 拿 409，这条断言必红。

**本次失败现场也与「只有一路成功」自洽**：`bug_log` §82 记的是 `revision=5 / coop.turn=2 / lastAction={seat:1,intent:"enter:1"}`。如果是「两路都被接受」，第二路会在 `turn=2` 上再 push 一次 `submitted` 并 bump 一次，`revision` 应比健康路径多 1（且 `turn` 仍是 2，因为 2 座位房只交齐了 1 个）。**「revision 没有多涨」本身就指向单次接受**。（严格说还需「健康路径的 revision 也是 5」这一步取证，见 §6。）

### 4.2 正确写法（当前 `e2e_p42e_coop.mjs:148-152` 已改成这个）
```js
const okCount = [ra, rb].filter((x) => x.status === 200).length;
const replayCount = [ra, rb].filter((x) => x.status === 409 && x.data?.code === 'INTENT_REPLAY').length;
suite.check(..., okCount === 1 && replayCount === 1, ...);
```
这个判据比旧断言**更严**（同时排除了「两路都 200」和「一路 500 一路 200」）。建议再补两点：
1. 显式断言「两路都不得为 5xx」，把「一路 500 导致另一路成为合法首提」这个 C1 机制也挡在门外；
2. 失败信息里带上两路的 `revision`（不只是 status/code），这样 §4.1 的判别就能自证。

### 4.3 仓库内早就有正确先例 —— 这是「用例写错」的最强旁证
`e2e_multi_instance.mjs:283-286` 的同 nonce 并发用例，从落地起就是 `okCount===1 && replayCount===1`。p42e 是全仓唯一把「第二路必须输」写死的地方（`grep INTENT_REPLAY` 共 9 处，仅此一处按数组下标断言）。同一个产品行为，两套用例两种断言，红的那套就是错的那套。

### 4.4 新增的 `e2e_p42e_nonce_race.mjs` 方向正确，但结论需以运行结果为准
它的 S3（`e2e_p42e_nonce_race.mjs:147-179`）用「给名义第一路加 30ms 延迟」把顺序反转，并断言「旧断言必然红、语义仍成立」——这正是把偶发变必现的正确构造。**我没有运行它，不对其绿化背书**；§6 给出取证清单。

## 5. 建议的验证顺序与修法优先级

**顺序（不可跳步）**：

1. **补取证**：一次绿跑 + 一次红跑，各自记录两路的 `status / code / revision / turn`，以及服务端日志里有无 `ROOM_CAS_CONFLICT` / Prisma `P2028` / `租约已易主`。

3. **定因**：若两路 code 落在 {200, INTENT_REPLAY} 且胜者 `revision` 只涨一次 → 断言错（预期结论）；若出现 5xx 或两路 200 → 转产品线排查（2.2 的连接池 / 租约）。
4. **修**：先改断言（已完成），再按需单独立项做产品加固。

**产品侧修法优先级**（与本次红灯解耦）：

| 优先级 | 事项 | 理由 |
|---|---|---|
| P1 | `retryCas` 挪出事务（或 savepoint） | 3.6 是唯一会静默写坏 quota 的点 |

**不改产品代码就能先做的 3 条加固**：
