## 0. 结论

四种玩法（单人打怪抓怪 / 单人 Boss 伤害排名 / 玩家互相对战 / 同屏共斗 Boss·副本）
**不会导致「决定不了服务器状态」，也不需要四套权威源**。P3-2 起「谁有权写状态」已钉死在服务端，
玩法差异只是「状态作用域 + 串行化粒度 + 广播范围」的组合。唯一缺口是**房间（room）这一层状态域**。

排期按风险递增分五阶段，每阶段独立可验收：

| 阶段 | 内容 | 风险 | 依赖 |
|---|---|---|---|
| **P4-2a** | 只读派生榜（4 类） | 最低 | P4-1 |
| **P4-2b** | 房间内核（无玩法，承载全部掉线/超时/次数口径） | 最高（但复用最彻底） | P4-2a |
| **P4-2c** | 单人 Boss 挑战 + 伤害排名（限次） | 低 | P4-2b |
| **P4-2d** | 玩家对战 1v1 | 中 | P4-2b |
| **P4-2e** | 共斗 Boss / 副本 | 中高 | P4-2b + c + d |

**三条不变式**（任何阶段都不破）：

1. 每个可变状态只有一个 owner key：`userId:slot` / `battleId` / `areaId` / **`roomId`**。
2. 每次写只有一个串行化键：`withSlotLock(key)`；房间态用 `room:xxx`（薄封装，锁本身零改动）。
3. 客户端只发意图、只收全量快照；`commitState()` 仍是写个人档的**唯一入口**。

## 1. 产品口径（2026-11-07 杰哥拍板）

| 条目 | 口径 | 服务端落点 |
|---|---|---|
| 基础玩法 | 目前单人打怪 / 抓怪；剧情到达一定进度后开放玩家对战与 Boss 挑战 | 解锁条件服务端判定，不做客户端开关 |
| 掉线 | 组队成员掉线 → **等待重连**，保留座位与回合态 | 房间成员状态机 `disconnected` |
| 全员掉线 | 都掉了 → **退出房间、不算次数**（限次 Boss） | quota `release`，不结算、不写伤害 |
| 托管 | 重连超时后，**仍在房间的另一个人可选**开启队友托管；托管如何放技能后续设计 | 托管是「可选项」不是自动接管；策略接口留空 |
| 限时 | 共斗**必须**限时；1v1 PK 超过 20 秒（暂定）不放技能 → 随机放；后续可能改设定 | 回合超时参数化，服务端 RNG 代放 |
| 榜单 | 单宠战力榜 / 全队战力榜 / 召唤师等级榜 / 推图榜（**暂定四类**） | 只读派生视图，客户端无写权限 |
| **战力口径（11-07 补充）** | 按**宠物六维总属性**算单只战力，**不代表更强**（血多只是耐揍）；后续宠物装备加攻击力/属性也会影响总战力 | 服务端对「有效六维」求和；**公式细节待定**，定义先钉死（见 §4） |
| **召唤师等级（11-07 口径修正）** | **人物的等级 = 账号等级**，不是进度派生值；**跟宠物最高等级挂钩**：账号 10 级则宠物最高只能 10 级（未来可能改成 `N+5`，规则可变但「账号等级决定宠物等级帽」不变） | 服务端持有账号等级真值 + 所有宠物等级写入口强制等级帽；客户端上报等级无效。P4-2a 当前是**占位派生**，待偿还（台账 F04） |
| **周期结算 / 榜单奖励（11-07 补充）** | **都会有**，未来再设计 | 周期结算任务 + 结算后服务端发奖，客户端无写权限（台账 F01 / F02） |
| **管理员污染榜单（11-07 补充）** | 后续做**单机隔离版**自测，隔离环境不进线上真值；**现在先不用纠结** | 保持 P4-2a 的「排除封号/管理员」兜底，不再投入（台账 F03） |

## 4. 五阶段拆分与验收口径

### P4-2a 只读派生榜（4 类）— ✅ 已实现（2026-11-07）

**为什么排最前**：零房间、零并发、零实时，是纯服务端读模型；能先把「服务端存档真值 → 派生 → 只读下发」链路验通，且不依赖任何后续阶段。附带修复一个真实数据缺口：全库**没有战力公式**（`data.ts` 的 `power` 只是技能威力），`SaveData` 也**没有 `playerLevel` 字段**。

**主要新增**：`game/power.ts`（战力纯函数：**只读「有效六维」求和**，系数 / 权重 / 取整待定）、`game/rank.ts`（派生口径）、榜单快照（Read Model + 周期刷新）、`GET /api/rank/:type`。

| 榜单 | 服务端派生口径（暂定） |
|---|---|
| 单宠战力 | 单只 = 有效六维之和；榜单取 `party ∪ box` 中最高一只 |
| 全队战力 | `party` 各只战力之和（不含 `box`） |
| 召唤师等级 | **⚠️ 占位派生**，不是产品口径：由 `clearedAreas` 首通数 + 队伍等级 + 图鉴捕获数派生。产品定义是「账号/人物等级 + 宠物等级帽」，见 §1 与台账 F04，**尚未实现** |
| 推图 | `clearedAreas` 数量与最高 `level` |

> **战力定义（2026-11-07 杰哥补充：公式待定、定义钉死）**
> - **单宠战力 = 当前有效六维之和**：`maxHp + atk + def + spAtk + spDef + spd`。
>   `StatBlock` 六维见 `src/game/types.ts:75`，个体当前面板直接存于 `MonsterInstance`（`maxHp/atk/def/spAtk/spDef/spd`），**不需要重算种族值 + 成长率**。
> - **必须用 `maxHp`，不能用 `hp`**：`hp` 是当前剩余血量，会随战斗、治疗、全灭惩罚波动；拿它算战力会出现「打一仗掉榜、回血刷榜」，且和「不代表实战强弱」的定位冲突。
> - **战力不代表实战强弱**：血多只说明耐揍，不体现技能、属性克制、速度先手、异常、PP 与捕获难度。榜单 UI 必须标注「仅六维总和，不代表强弱」；**战力不得用于匹配、伤害、奖励、解锁或任何判定**（否则它变成隐藏实力分数，必然被刷）。
> - **公式本身待定**：系数 / 权重 / 取整 / 等级修正后续可调，先按简单求和占位；实现为服务端纯函数，输入只依赖有效六维，可复现、可单测。杰哥明确「有这个榜单和这个规划就好」，故 P4-2a 开工前不锁死数值细节。
> - **宠物装备的扩展点**：后续装备加攻击力或其他属性时，加成作为**服务端独立真值**叠加成 `effectiveStats = 基础面板 + 装备加成`，战力函数仍只读有效六维 —— **装备上线时战力函数零改动**。装备加成**不写回 `MonsterInstance` 面板**，避免污染 `digestOf` / authority 摘要与 CAS 风控（否则会被判「凭空变强」）。不要把种族值 / 等级 / 技能 PP 塞进战力输入，否则装备一来就要维护两套口径。

> **召唤师等级：2026-11-07 口径修正，当前实现是「已知偏差」而非产品定义**
> - **产品定义（杰哥）**：召唤师等级 = **人物 / 账号等级**，与宠物最高等级挂钩；账号 `L` 级 → 宠物等级上限 `L`（未来可能 `L+5`，规则可变、关系不变）。等级帽由服务端在所有宠物等级写入口强制。
> - **当前实现（P4-2a 占位）**：`1 + 首通区域数×2 + floor(队伍等级总和/10) + 图鉴已捕获物种数`，纯派生、**不加持久化字段**。这是四个榜单都暂定时避免锁死存档结构的临时决定，**不符合产品定义**。
> - **为何当时不加字段**：新增 `playerLevel` 必须同步 `SCHEMA_VERSION`（`src/game/saveVersion.ts`）、`EXPECTED_SAVE_VERSION`（`backend/src/lib/saveValidator.ts`，当前 10）与 migrate 分支三处；老存档还要能玩。
> - **偿还**：独立子项，见 `未来规划与技术债_2026-11-07.md` **F04**（含经验/升级规则、等级帽校验、榜单改读真值、UI 文案）。**在此之前不得声称该功能已实现**；`RANK_META` 描述已标「占位」。不阻塞 P4-2b（房间层不读召唤师等级）。
> - 同理，「剧情解锁 PVP / Boss」也先用服务端派生门槛，不做客户端开关（F09）。

**验收**：客户端伪造上报战力 / 等级 / 推图进度 / 排名分数一律忽略或 400；改档被 CAS 与风控挡；四张榜各一条端到端用例；**战力取 `maxHp` 不取 `hp`**（同一只宠受伤 / 治疗前后战力不变）、**战力不参与匹配 / 伤害 / 奖励 / 解锁任何判定**；`GET /api/rank/*` 只读、无写入口；**不动 `SCHEMA_VERSION`**；`npm run verify` 20 阶段全绿。

**明确不做**：榜单奖励、跨服榜、实时逐帧刷新、观战。

> **实现记录（2026-11-07，tx 自选决策，不改动上面的产品口径）**
> - **文件**：后端 `game/power.ts`（`effectiveStats` / `monsterPower` / `partyPower` / `bestMonsterPower`）、`game/rank.ts`（四榜派生与稳定排序）、`modules/rank.ts`（只读接口）；前端 `lib/rank.ts`、`components/RankBoardModal.tsx`，入口在 `Camp.tsx` 顶部第二行「榜单」。
> - **接口**：`GET /api/rank` 返回四榜元数据；`GET /api/rank/:type?limit=1..50` 返回只读榜单。**只有 GET**，POST/PUT 一律 404；显式携带 `power` / `playerLevel` / `clearedAreas` / `score` 等伪上报字段 → 400 `RANK_INPUT_FORBIDDEN`；未知类型 → 400 `RANK_TYPE_UNKNOWN`。`GET /api/health` 加 `rank` 统计。
> - **读模型实现决策**：契约原写「快照 + 周期刷新」，P4-2a 落地为**每次请求从 DB 落库真值实时派生**（等价 TTL=0 的 Read Model），不缓存、不落库。理由：原型规模小、写档后立刻可见、避免「刚打完仗榜单还是 30 秒前」的陈旧态；后续有规模再换周期快照，**接口与前端零改动**。真值来源是 `Save` 表（`commitState()` 写内存必落 DB），读时先过 `validateSaveData()`，脏档不上榜。
> - **排除**：封号账号、管理员账号。管理员可用测试菜单造满属性/满金币，放进全服榜会污染数据（与反作弊分级口径一致）。
> - **召唤师等级具体公式**（派生，不落字段）：`1 + 首通区域数×2 + floor(队伍等级总和/10) + 图鉴已捕获物种数`，上限 9999。推图榜主值 = 首通数，同数量时比较最高区域 `level`（secondary）；同分再按用户名 / 槽位稳定排序。
> - **战力公式仍待定**：按杰哥口径只做「有效六维简单求和」占位，系数 / 权重 / 取整 / 等级修正均未实现；`maxHp` 而非 `hp`、不参与任何判定、装备加成走 `effectiveStats` 三条边界已由单测与 E2E 钉住。
> - **验收**：`npm run verify` 22 阶段全绿；后端 249 / 前端 105 单测；`e2e:p42a` 39 例 `E2E_P42A_OK`；375px `ui_smoke_p42a` 17 例 `UI_SMOKE_P42A_OK`；**`SCHEMA_VERSION` 未动**。详见后端规范 §23、bug_log §28。

### P4-2b 房间内核（无玩法）— ✅ 已实现（2026-11-07，风险最高，一次做掉所有口径）

**为什么排第二**：杰哥给的三条口径（掉线等待重连 / 全员掉线不扣次数 / 超时托管 / 回合限时）**都是房间层通用能力**。先在这层用假玩家跑通，c / d / e 只填结算逻辑，不各做一遍。

**主要新增**：`lib/roomRegistry.ts`（`roomId`、成员座位、状态机 `forming → active → paused → abandoned | settled`、`roomRevision`）、`withRoomLock(room:xxx)`、`room.state` 全量快照 + `broadcastRoom()`、`room.action` 上行意图、存储适配器接口（见 §5）。

**掉线 / 超时状态机**：

1. WS 断 → 座位标记 `disconnected`，**保留**回合态与座位，推 `room.state` 给房内其他人。
2. **同一 token 同一设备**重连 → 原位恢复，推全量快照；超时计时清零。
3. 掉线超 `AUTOPILOT_OFFER_MS` → 房内其他**在线**成员可以开启托管（不是自动托管）；托管 MVP 用 `pickUsableMove()` 随机放，策略接口 `AutopilotPolicy` 留空，后续 AI 直接替换。
4. 全员掉线超 `ALL_OFFLINE_GRACE_MS` → 房间 `abandoned` 解散，**quota release、不扣次数、不结算、不写伤害事件**。
5. 回合超 `ROUND_TIMEOUT_MS` → 服务端用注入 RNG 代放一个可用技能，正常推进回合，广播快照。

**限次次数（quota）三段式**：进入时 `hold`（只校验余量、不消耗）→ 正常结算 `commit` → 解散 / 全员掉线 `release`。三段都在 `withRoomLock` 内、幂等、**绝不在客户端扣**；这样「都掉了不算次数」是结算时机问题，不是补偿逻辑。

**与 P4-1 顶号的关键边界**：换设备登录会递增 `sessionVersion`，旧 token 所有 REST 403 `SESSION_REPLACED`。因此**只有同一 token 同一设备算重连**；换设备登录按「成员掉线」处理，不自动转移座位，也不把新连接塞进旧房间。房间广播按 `userId` 走 `broadcastToUser()` 的并集。

**验收**：双假玩家跑通「开局 → 掉线 → 30s 可选托管 → 重连 → 20s 超时随机放 → 全员掉线解散不扣次数 → 正常结算扣一次」；伪造 `room.state` 上行被拒并关 1008；`roomRevision` 单调且客户端幂等应用；**照 P4-0 的 `slotLock.test.ts` 做法补去锁确定性单测**（E2E 并发形状证明不了临界区，bug_log §26）；所有阈值可从服务端配置改。

**明确不做**：真实匹配、伤害计算、奖励分配、玩法 UI。

## 5. 硬门槛与已知边界

- **单进程假设**：`WildRegistry` / `RoomRegistry` / `slotLock.ts` 都是单进程内存态，`claim()` 靠「Node 单线程无 `await`」保证原子（规范 §22.7）。同一房间请求落到两个进程，Boss HP 与次数会直接分叉。**P5-1 多实例部署前必须把野怪 / 房间 / 锁统一迁到共享存储 + 分布式抢占**；因此 P4-2b 的 `RoomRegistry` 必须做成「纯逻辑 + 可替换 storage adapter」，不要在每个玩法里各做一遍。
- 客户端**永远不能上报真值**：伤害、HP、战力、排名分数、quota 消耗、区域等级。
- 顶号语义（§22）不变：同账号后来者登录，前者只读下线。
- 新增持久化字段必须同步 `SCHEMA_VERSION` / `EXPECTED_SAVE_VERSION` / migrate（项目硬约束）；P4-2a 刻意不加字段就是避开它。
- 改 `src/game/data.ts` 必须 `cd backend && npm run gen:content` 并一起提交。
