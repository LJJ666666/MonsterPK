# p42e nonce 去重竞态：设计与复现方案

- 日期：2026-11-16
- 状态：**设计稿，未动一行产品代码**。等杰哥拍板 + 可邀请后端设计专家评审后再实施。
- 关联：bug_log §82（现象）、§82 订正、`backend/tests/e2e_p42e_coop.mjs`、`backend/src/modules/room.ts`、`backend/src/lib/roomRegistry.ts`、`backend/src/lib/pgRoomStorage.ts`、`backend/src/lib/roomUnitOfWork.ts`

## 1. 结论先行

1. **最直观的假设已被源码排除**：房间 action 路由不是「无锁裸跑」。`applyRoomIntent` 整段在
   `withRoomUnit(roomId, ...)` 内（`room.ts:290`），而 `withRoomUnit` = `withRoomLock(roomId)` +
   同一 PostgreSQL 事务（`roomUnitOfWork.ts:92`）；写回还有 `updateMany({where:{revision: base}})`
   行版本 CAS（`pgRoomStorage.ts:68`）。所以「补一把锁」解决不了它。
2. **当前更像「语义漏洞」而不是「并发窗口」**：`seenNonces` 是**房间态里的一个数组**，随
   `Room.data` 的 JSON 一起写回；只要某一次写回把不含该 nonce 的旧副本落库，去重依据就丢了。
   慢环境只是让这条路径更容易被踩到，不是根因。
3. **下一步不是改代码，是先把它变成确定性可复现的红灯**。现在单跑 3/3 绿、全量偶发 1 红，
   在拿到「稳定红 → 改完稳定绿」之前，任何修法都无法验收。

## 2. 已知事实（全部来自源码与失败现场）

| # | 事实 | 证据位置 |
|---|---|---|
| F1 | REST `/action` 与 WS `room.action{intent}` 都走 `applyRoomIntent` | `room.ts:290` |
| F2 | `applyRoomIntent` 全程在 `withRoomUnit`（房间锁 + 事务）内 | `roomUnitOfWork.ts:92-94` |
| F3 | 去重判据是 `room.seenNonces.includes(nonce)`，命中返回 409 `INTENT_REPLAY` | `roomRegistry.ts:565` |
| F4 | `seenNonces` 只增不减（上限 64，超出丢最旧），**回合推进不清空**（只清 `submitted` / `turnIntents`） | `roomRegistry.ts:570`、`627-628` |
| F5 | 写回按 revision CAS，冲突抛 `RoomCasConflictError` → `retryCas` 整段重跑（最多 5 次） | `pgRoomStorage.ts:68`、`roomRegistry.ts:801` |
| F6 | 失败现场：`revision=5`、`coop.turn=2`、`lastAction={seat:1, intent:"enter:1"}` | bug_log §82 |

**F3~F5 合起来说明**：只要第一路真的把 nonce 落库了，第二路无论读新读旧都不该拿到 200——
读新则 `seenNonces` 命中；读旧则 CAS 失败重跑后命中。**所以「200」意味着那一刻落库的
房间态里确实没有这个 nonce**，即第一路要么回滚了、要么写回的副本不含它。

## 3. 候选根因（按可能性排序）与判别实验

| 编号 | 假设 | 判别方式 |
|---|---|---|
| C1 | **第一路请求自己失败了**（409 冲突耗尽 / 事务超时 / 其他错误），nonce 随回滚消失；第二路于是成为「合法首提」，200 且推进回合 | 记录**两路各自的** status + code + 耗时。测试现在只看第二路，第一路的结果没留证 |
| C2 | `seenNonces` 被**旧副本覆盖**：某条不走 `submitIntent` 的写路径（如 `markDisconnected` 的 `withUserRooms`、`tick`、`writeBack`）拿着更早的 `RoomState` 副本写回，把 nonce 冲掉 | 在 `pgRoomStorage.set()` 打点：写回前 `seenNonces` 长度 + revision + 调用来源；复现时看是不是「变短了」 |
| C3 | **多实例 + 跨进程**：写回 CAS 只在行级成立，但两路读到的副本来自不同实例的本地缓存（若有） | 复现时固定 `MPK_DISABLE_SWEEP=1` 单实例跑一遍、双实例跑一遍，比对命中率 |
| C4 | **测试前提本身不成立**：两路并发时，第一路可能先被判 `TURN_ALREADY_SUBMITTED`（同座位本回合已提交），测试却只断言「409 且 code=INTENT_REPLAY」，第二路 200 其实是新回合的合法提交 | 断言里加上「第一路必须是 200 或 INTENT_REPLAY」的前置，先确认测试语义 |

C1 与 C4 都指向同一个工程结论：**当前 e2e 对「谁该被拒」这个前提没做校验**，红的时候无法区分
「产品错」还是「测试错」。这一条无论根因是什么都要补。

## 4. 复现方案（先做这个，不动产品代码）

目标：把「偶发」变成「必现」，且在 CI 慢环境与快环境都稳定。

1. **加宽并发窗口**：两路请求之间插入可配置延迟（默认 0ms，复现时 50~200ms），
   覆盖「第一路已进临界区、第二路在门外」的真实时序。
2. **放大事务耗时**：用测试内注入（`setRoomUnitRunnerForTest`，已存在于 `roomUnitOfWork.ts:49`）
   给事务加人为耗时，模拟慢环境；**不改生产默认值**。
3. **两路结果全量取证**：status / code / 耗时 / `revision` / `seenNonces` 长度 / `coop.turn`
   一起打，失败时直接产出可判定证据，而不是只报「第二条期望 409 得到 200」。
4. **重复跑**：同一用例连跑 30 轮，要求「200 的条数恒为 1」；这是后续验收的硬指标。

## 5. 修法候选

| 方案 | 做法 | 优点 | 代价 / 风险 |
|---|---|---|---|
| **A. nonce 硬去重表（推荐）** | 新表 `RoomNonce`，主键 `(roomId, nonce)`；提交前 `INSERT`，唯一约束冲突即判重放 | 与锁、事务、CAS 全都无关，**跨进程/跨实例/跨回合都成立**；也和 F04、F18-d 的「展示/去重类状态走独立表」范式一致 | 多一次写；要定 TTL / 清理策略（房间删除时级联或按 sweep 回收） |
| B. 房间态内去重 + 强制重读 | 每次提交前 `SELECT ... FOR UPDATE` 重读房间态 | 不动 schema | 依赖行锁粒度，跨实例仍要靠 DB 行锁；`seenNonces` 数组仍有被旧副本覆盖的风险 |
| C. 幂等响应缓存 | 同 nonce 重放**返回首次结果**（200 + 同一份 view），而不是 409 | 客户端连点体验最好，天然幂等 | 要存 nonce→首次响应；只解决「重复提交」，不解决「旧副本冲掉 nonce」 |
| D. 什么都不改，只加固测试 | 明确「第一路失败则本用例跳过」 | 零风险 | 掩盖真实风险：生产上连点两次确实可能被当两次提交 |

**建议顺序**：先 §4 复现 → 用 C1/C2 判别实验定因 → 若确认是「旧副本覆盖」或「回滚后重提」，
直接上 **A**（一次性把去重从「房间态数组」搬到「唯一约束」，永久消除这一类竞态）；
**C** 作为后续 UX 优化单独立项（客户端连点更友好），不要和 A 混在一单里。

## 6. 验收判据（改完必须全部满足）

1. §4 的确定性复现用例：改前稳定红、改后连跑 30 轮绿；
2. 两路并发同一 nonce：**200 恒为 1 条**，另一条 409 `INTENT_REPLAY`（或按 C 方案返回同一份幂等结果）；
3. 跨回合、跨 `advanceTurn`、跨「掉线重连」后重放仍判重；
4. 双实例（`MPK_DISABLE_SWEEP=1` 单实例 + 真双实例两轮）都成立；
5. 既有断言一条不放宽，`npm run verify -- --strict` 全绿；
6. 若引入新表：走迁移、加进 `check:inventory` 的模型清单、同步 `saveValidator` 无关（不动存档契约）。

## 7. 留给后端设计专家评审的问题

1. 去重键的**作用域**该是 `(roomId, nonce)` 还是 `(roomId, seat, nonce)`？现在客户端 nonce 是否含座位信息？
2. nonce 生命周期：跟着房间 TTL 走，还是固定窗口（如 10 分钟）？需不需要 `RoomNonce` 的清理任务？
3. 409 vs 幂等回放：哪种语义更符合「连点两次」的产品预期？要不要按 `intent` 类型区分？
4. 「旧副本覆盖」这一类问题在其它写路径（`tick` / `markDisconnected` / `writeBack`）是否也存在？
   要不要统一收敛成「只允许 `loadAndMutate` 写房间态」的硬约束？
5. 是否值得把 `RoomState` 的 JSON 整体写回换成列式/版本化字段，降低「整包覆盖」的固有风险？
