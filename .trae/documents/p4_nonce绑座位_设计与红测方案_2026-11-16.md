# P4（nonce 绑定座位）设计与红测方案 — 2026-11-16

> 口径来源：`bug_log.md` §88「P4 nonce 未绑定座位」；后端设计评审 `p42e_后端设计评审_专家意见_2026-11-16.md` §2.4 / §3.2 / §3.8（专家表中编号 P5，项目台账中编号 P4，本文一律用**项目台账编号**）。
> 状态：**已按方案 B 实施并验收（bug_log §89）**。本文禁止与已关闭的 p42e 红灯（§85 断言错）混单。

## 1. 问题定义（现在到底错在哪）

`backend/src/lib/roomRegistry.ts` 的 `seenNonces: string[]` 是**全房间共用**的一维数组：

- `submitIntent`（589-594）：`room.seenNonces.includes(params.nonce)` → 命中就 409 `INTENT_REPLAY`；未命中就 push，超 64 条 `shift()`。
- `offerAutopilot`（558-563）：同一数组、同一套判定，只是 nonce 来自 WS 上行。
- `RoomState.seenNonces`（`roomTypes.ts:116-117`）注释只写「已消费的意图 nonce」，没写作用域。

后果：

1. **跨座位抢占**：座位 A 用过的短 nonce，座位 B 再用就被 409；A 的提交仍然成功。一个成员（或一条迟到的旧请求）可以挡住另一个成员的重试。
2. **测试/短 nonce 必撞**：仓库里 nonce 并不都是 UUID —— `src/lib/pvp.ts:15-19` 是 `Date.now(36)+seq(36)+Math.random(36)`，E2E 里大量 `enter:0`/`rev_g1` 这类短串；只要两人同时用同一个串，就会误判。
3. **服务端无法区分「同一人重放」和「另一个人首次提交」**：这是语义缺口，不是概率问题。用户离线队列补发时尤其容易踩。

## 2. 目标 / 非目标

**目标**：把去重键的作用域从「房间」收紧到「房间 + 座位」，让不同座位使用相同 nonce 互不干扰；同座位重放仍 409。

**非目标**（本单明确不做，留给其他工单）：

- 64 条 `MAX_SEEN_NONCES` 窗口淘汰导致的「老 nonce 重放被接受」（专家 §2.1 / §3.1）—— 属唯一约束表工单。
- REST 层正则不含冒号、内核 `validIntent` 含冒号的规则漂移（专家 §3.2）。
- `normalizeRoom` 补数组字段（项目台账 P5 / 专家 P4）。
- 注释口径清理（P6）。

## 3. 方案对比

| 方案 | 改动 | 优点 | 致命点 | 结论 |
|---|---|---|---|---|
| A. 强制客户端全局 UUID nonce，保持 `(roomId, nonce)` | 改 `pvp.ts`、全部 E2E/UI 冒烟的短 nonce；服务端不变 | 去重键最简单 | ① 不能防恶意复用（别人拿到 UUID 照样抢）；② 测试资产要大改；③ 与「服务端权威」不一致——把正确性押在客户端自律上 | 否 |
| **B. 服务端把落库键改成 `${seat}:${nonce}`** | 只改 `roomRegistry.ts` 两处判定 + 一处 helper；类型不变、schema 不变 | 零迁移、零 schema 变更、零跨端改动；语义直接对齐「谁提交」 | 旧房间里的裸串不再参与去重（见 §5 风险） | **推荐** |
| C. 独立表 + `(roomId, seat, nonce)` 唯一约束 | Prisma migration + 事务内 INSERT + 级联清理 + 幂等响应策略 | 顺手关掉 64 窗口与整包覆盖两类问题 | 改动面大，需停 :3001 改 schema；本单只想修语义缺口，不宜夹带 | 留作后续工单 |

**分隔符安全性**：nonce 允许 `:`，但键固定取**第一个冒号前**为十进制座位号；`1:2:abc` 与 `12:abc` 必定不同，无歧义。`validIntent` 的 `≤64` 上限不变（拼前缀后数组元素最多 67 字符，仅内存/JSON 文本，不参与该正则）。

## 4. 详细改动点（拍板后执行）

1. `backend/src/lib/roomRegistry.ts`
   - 新增纯函数（模块级、不导出亦可）：
     ```ts
     function seenNonceKey(seat: number, nonce: string): string {
       return `${seat}:${nonce}`;
     }
     ```
   - `submitIntent`（589-594）：`includes`/`push` 一律用 `seenNonceKey(seat.seat, params.nonce)`；顺序保持「先判重放 → 再 push → 再判 `TURN_ALREADY_SUBMITTED`」，§88 P3 语义不变。
   - `offerAutopilot`（558-563）：用 `seenNonceKey(actor.seat, params.nonce)`（actor 已由 `actorUserId` 定位），不使用 `target.seat`。
   - `MAX_SEEN_NONCES` 保持 64，注释补一句「数组元素是 `${seat}:${nonce}`，淘汰语义见 bug_log §88」。
2. `backend/src/lib/roomTypes.ts:116-117`：注释改为「已消费的意图去重键，元素形如 `${seat}:${nonce}`；作用域为房间+座位」。
3. `backend/tests/p1p3RoomSettle.test.ts:132`：原断言 `seenNonces.includes('n_late')` 随键格式改为 `includes('0:n_late')`（或行为级断言，二选一，不放宽）。
4. 新增确定性红测 `backend/tests/p4SeatNonce.test.ts`（本轮已落盘，见 §5）。
5. 文档：`bug_log.md` 新增 §89 记录红→绿证据；`MEMORY.md` 把 P4 从「留白」改为「已修」，同步镜像；`doc_check` 锚点不增删。

## 6. 风险与兼容口径

- **旧房间残留**：当前 PG 里若还有部署前的房间，`seenNonces` 存的是裸串；新判定用 `${seat}:${nonce}`，老串不会命中，等于一次性清空去重历史。项目无老用户、房间是测试态，接受；但必须在 §89 写死，不能悄悄混过去。
- **64 窗口仍在**：本单只换键，不换存储，超 64 条的老键重放仍可能被接受 —— 明确留白，不宣称「已彻底防重放」。
- **多座位共谋**：不同座位各发自己的 nonce 仍可正常提交，这是预期行为；去重不负责限制提交频率（那是 quota/租约的职责）。
- **不引入新 schema、不升 `SCHEMA_VERSION`、不动存档**：纯房间态内部键格式变更。
