## 0. 结论摘要（先看这里）

**一句话：不能「只换一个 `RoomStorage` adapter」。** 单进程假设散落在 **8 类进程内状态 + 1 个进程内锁 + 2 个周期定时器 + 全部 WS 广播 + CAS 版本源** 上，必须成组迁移；单独换掉任一块都会产生更隐蔽的分叉。

三个被现有文档低估、且会直接改变排期的点：

| # | 发现 | 证据 | 后果 |
|---|---|---|---|
| 1 | **`revision` 不是 DB 独立列**，藏在 `Save.authority` JSON 文本里；CAS 基线取自「在线内存权威态」 | `backend/prisma/schema.prisma:59-61` 注释、:50-63 model；`modules/save.ts:124-126` `currentState()`；`lib/revision.ts:39` 注释「内存权威态优先，回落到 DB」 | 规范 §21.3 的 `UPDATE ... WHERE revision = ?` **当前无法直接实现**；多实例下各进程内存副本分叉，正常写入会被误判 409。**必须先把 revision 提为独立列、并以 DB 为唯一真值**，这是阶段 0 的硬前置。 |
| 2 | **`RoomStorage` 是同步接口，且内存实现返回同一对象引用** | `lib/roomRegistry.ts:26-34` 七个方法全同步；:42-48 `get()` 直接返回 Map 里的对象；:110-118 / :297-306 等全篇「先改字段、再 `bump()` 里 `set()`」 | 换成 Redis/Postgres 必然变异步 + 序列化，不是薄替换：`RoomRegistry` 约 600 行状态机要同步→异步重写，并补显式版本 CAS，否则丢失更新。台账 F10 的「只换 adapter」口径**偏乐观**。 |
| 3 | **两个 `setInterval` 每个进程各跑一遍，且房间 sweep 不持锁** | `modules/realtime.ts:154`（心跳）、:216（房间 250ms）；`modules/room.ts:108-109` `sweepRooms()` 直接 `rooms.sweep()`，无 `withRoomLock` | 多实例会重复推进回合、重复补怪、重复释放 quota、重复触发结算 → 双发奖。必须「选主 + sweep 幂等兜底」双保险，不能只靠锁。 |

**总量评级：L。** 跨 6 个耦合点、第 12 条 Prisma 迁移、25 组 E2E + 15 组 UI 冒烟需扩双实例场景。建议按第 5 节 8 个阶段推进，**1.1 完成前不要开第二个实例**。

## 2. DB 侧已经天然安全的部分（不要重做）

| 机制 | 证据 | 说明 |
|---|---|---|
| 发奖幂等 | `schema.prisma:181` 注释：`grantKey @unique` / `@@unique([roomId,userId])`，**不取应用层锁** | `BossRewardGrant` / `CoopRewardGrant` / `BadgeGrant` / `AchievementGrant` 靠唯一索引挡重复，Postgres 下天然跨实例安全 |
| 伤害/次数真值 | `BossDamageEvent`、`BossDamageEvent.battleId @unique`（:93） | 按自然日计数在库，进程重启不重置（`bossQuota.ts:4-9` 已刻意区分「房间临时态 vs 账号日配额」） |
| 意图防重放 | `IntentLog @@unique([userId, nonce])`（:75） | 同上 |
| 顶号「数据面」 | `User.sessionVersion` + `lib/account.ts:23-31`，REST 守卫每请求查库 | 旧 token 的 REST 跨实例仍会 403 `SESSION_REPLACED`；**但「实时面」不安全**，见 3.5 |
| 存档写入唯一入口 | `modules/session.ts:97-135` `commitState()`：DB upsert → 更新内存态 → 广播 | 顺序本身正确，问题只在内存态被当成权威源 |

**结论：要迁的是「实时态 + 锁 + 广播 + 版本源」，不是「奖励真值」。** 别把已落库的真值搬进缓存。

> ⚠️ 版本号有两个不同概念，别混：`SCHEMA_VERSION`（前端存档 JSON 版本，当前 **11**，见 `lib/saveValidator.ts:26`）与 **Prisma 迁移链**（当前 **11 条**）互不相关。新增第 12 条迁移只是给 `Save` 加 `revision` 列，**存档 JSON 结构没变 → 不动 `SCHEMA_VERSION`、不补 migrate 分支、不动 `EXPECTED_SAVE_VERSION`**。

## 3. 六个必须成组改造的耦合点

### 3.1 版本源与 CAS（最高优先）
- 现状：`checkWriteRevision(currentRev, …)` 的 `currentRev` 来自 `currentState()`，内存权威态优先；`authority.revision` 随 `commitState()` 在内存里 `monotonicAuthority` 单调推进。
- 建议：① `Save` 增 `revision Int` 独立列并回填现有 `authority` JSON 里的值；② `commitState()` 改成**事务内条件更新**（`UPDATE Save SET ..., revision = revision + 1 WHERE userId = ? AND revision = ?`，受影响行数为 0 即 409）；③ 内存态降级为**只读缓存 + 失效广播**，不得参与 CAS 判定。
- 验收：两个进程并发 PUT 同一账号，恰好 1 成功 1 返回 409；`revision` 严格 +1 不跳号。

### 3.2 锁
- 现状：`withSlotLock` 的 `chains: Map`（`slotLock.ts:15`）；只锁路由层，`commitState()` 不取锁以免自锁。
- 建议：保留**同样的 key 与顺序**，实现换成租约锁（Redis `SET NX PX` + fencing token）或 Postgres advisory/行锁；条件更新（3.1）作为**最后一道兜底**，即使锁失效也不会写脏。
- 注意：`alreadyLocked`、`rank:settle:*`、嵌套两把锁的顺序都要保留；锁超时需续租，且业务耗时上限要测（房间 tick 250ms 量级，Boss 结算含 DB 写）。

### 3.3 quota（在途闸）
- 现状：`BossQuotaLedger.hold()` 同步 Map（`bossQuota.ts:24-31`）；房间 `holdQuota()` 同步读改写（`roomRegistry.ts:194-200`）。台账 F10 / 规范 §… 已明确「换异步 adapter 时 quota 必须另加 key 级锁，否则会超卖」。
- 建议：把 `hold` 做成共享存储的原子自增 + TTL 租约（key 仍是 `bossQuotaKey` / `coopQuotaKey` / `room quotaKey`），`commit` 由 DB 事件/唯一索引体现、`release` 只删租约；TTL 到期自动归还，覆盖「进程崩了没 release」。
- 注意：`battle.ts:530-532` 与 `mapBoss.ts:237` 的 abandon 释放口径（`state.bossQuotaKey`）要一并核对，别漏分支。

### 3.4 定时器与选主
- 现状：`realtime.ts:154` 心跳（清死连接 / 封号复查 / `sweepSessions` / `battles.sweepExpired` 释放 quota / `wilds.sweep` 补怪并广播）、`realtime.ts:216` 房间 250ms sweep；`room.ts:108-109` 无锁。
- 后果：N 个实例 = N 份推进 → 野怪每区补到 3×N、房间回合推进 N 次、quota 释放多次。
- 建议：① 用租约选主，只有 leader 跑全局 sweep（心跳里的「本进程连接健康检查」仍各跑各的，这部分天然是本地的）；② 即使选主，房间/野怪的推进仍要在共享态上带版本 CAS 做幂等兜底，防止 leader 切换瞬间重叠；③ 广播从「sweep 内直接 `publishXxx`」改成「状态变更后发 pub/sub 消息」，由各实例各自推给本地连接。

### 3.5 广播与顶号
- 现状：`broadcastAll` / `broadcastToUser` / `broadcastToMany` 全部直接调本地 `wsRegistry`（`sessionBus.ts:31-43`）；`publishWild` 走 `broadcastAll`（`wild.ts:57-64`）；顶号 `kickUserConnections()` 只遍历本进程连接（`auth.ts:73`、`realtime.ts:61-72`）。
- 后果：A 实例写入的状态推不到 B 实例的连接；新设备在 B 实例登录时，A 实例的旧 WS 连接不会被踢（REST 已被 403，但连接会残留到心跳扫到）。
- 建议：三种广播改为 pub/sub 频道（全员 / `user:<userId>` / `area:<areaId>` / `room:<roomId>`）；每个实例订阅后只向**自己的**连接发送；顶号与封号的 `bye` 走 `user:<userId>` 频道广播，而不是只动本地表。

### 3.6 房间 / 野怪状态机同步→异步
- 现状：`RoomStorage` 七个方法全同步、`get()` 返回可变引用；`WildRegistry.claim()` 靠「无 await + 遍历 `byId`」保证「同账号仅一场战斗」（`wildRegistry.ts:258-262`）。
- 建议：
  - 房间：`RoomStorage` 改 async + 显式 `load/modify/commit` 事务或 Lua；`RoomState` 需可 JSON 序列化（含 `pvp`/`coop`/`seenNonces`，当前是纯数据，可行）；`bump()` 的 revision 变成共享 CAS 条件。
  - 野怪：`claim` 用 Lua/事务一次性完成「判状态 + 判同账号在途 + 置 claimed」；把「同账号在途」从全局遍历改成按 `userId` 的索引键 + TTL。
  - 二者都保留「按接收者裁剪视图」（`roomRegistry.ts:157-184`），别把 `pvp`/`coop` 全量下发。

## 4. 选型对比（需杰哥拍板）

| 维度 | A. 纯 Postgres | B. Postgres + Redis（**推荐**） | C. 不迁移，单实例纵向扩容 |
|---|---|---|---|
| 真值存储 | Postgres | Postgres（**Redis 不存真值**） | SQLite/Postgres 单实例 |
| 锁 | 行锁 / advisory lock + 条件更新 | 租约锁 + fencing token，条件更新兜底 | 现有 `slotLock` |
| TTL / 过期 | 需自己写过期扫描 | 原生 TTL，直接对应现有 5 处 TTL | 内存 Map |
| 广播 | `LISTEN/NOTIFY`（无持久订阅保证、无重放） | pub/sub（同样需兜底，但语义直接对应 `broadcastAll`） | 本地 |
| 组件/运维 | 少一个组件 | 多一个 Redis（需高可用） | 最少 |
| 与现有 TTL 语义契合 | 一般 | **好**：`BATTLE_TTL_MS` 30min / `SESSION_TTL_MS` 10min / `WILD_TTL_MS` 5min / `WILD_CLAIM_TTL_MS` 30min / 馆主 CD 20min | 好（单进程） |
| 满足 P5-1 多实例 | 可 | 可 | **否** |

**推荐 B**，理由：现有状态几乎全是「带 TTL 的临时态」，Redis 的 TTL/租约/pub-sub 与之一一对应，改造最直白。但必须钉死一条硬约束：**Redis 只放锁、租约、TTL 键与消息；权威真值只在 Postgres**。否则会引入第二真值源，直接违反三条不变式的第 ① 条。
若杰哥要求「组件最少」，A 也可行，代价是补租约续期、过期补偿扫描，以及 `LISTEN/NOTIFY` 丢消息时的兜底拉全量。C 只能缓解，不满足 P5-1 目标，不建议当成交付。

## 5. 分阶段顺序（建议，非既定排期；不可跳步）

| 阶段 | 内容 | 依赖 | 量 | 验收要点 |
|---|---|---|---|---|
| **1.0 前置** | 第 12 条迁移（`Save.revision` 列 + 回填）、`provider` 切 Postgres、环境变量 `DATABASE_URL` / `CORS_ORIGIN` / `VITE_API_BASE`、HTTPS、备份与回滚演练 | 需云环境/凭据 | M | 单实例全量 `verify` 零回归；`revision` 回填无跳号 |
| **1.1 锁与 CAS** | revision 提列 + DB 条件更新 + 分布式锁（保持 key/顺序/非重入）；内存态降级为缓存 | 1.0 | **L** | 跨进程并发 PUT 恰好 1 成功；`slotLock.test.ts` 不变量保持 |
| **1.2 定时器选主** | 租约 leader + sweep 幂等兜底 | 1.1 | M | 双实例跑 5 分钟，野怪每区恒 3 只、房间回合无重复推进 |
| **1.3 广播 / 顶号** | pub/sub 频道化 + 跨实例 `bye` | 1.1 | M | A 实例写入，B 实例连接收得到快照；跨实例登录能踢旧 WS |
| **1.4 房间 + quota** | `RoomStorage` 异步化 + 显式 CAS + quota key 级原子锁 | 1.1/1.2/1.3 | **L**（最大） | 同房间双意图只推进 1 回合、奖励只发 1 份、每日上限不超卖 |
| **1.5 野怪池** | Lua 原子 `claim` + `userId` 在途索引 | 1.1/1.2 | M | 同 wildId 双 claim 只 1 成功；超时归还 |
| **1.6 战斗/会话/馆主 CD** | 共享 KV + TTL，或按 `userId` 粘性路由先降级 | 1.1 | M | 换实例不丢战斗、CD 不可绕过 |
| **1.7 双实例回归** | 新增双实例 E2E + 全量回归 | 全部 | M | 见第 7 节 |

顺序理由：1.1 不先做，后面所有共享态写入都没有串行保证；1.2/1.3 必须早于 1.4，否则房间推进会重复且状态推不到对端；1.4 与 1.5 共用锁实现，可并行开发但需同一把锁的语义一致；1.6 允许用粘性路由先降级，降低一次性风险。

## 6. 风险与回滚

| 风险 | 对策 |
|---|---|
| 把 Redis 当真值 → 双真值源分叉 | 硬约束：真值只在 Postgres；Redis 仅锁/租约/TTL/消息 |
| 锁过期后旧持有者继续写 | fencing token + DB 条件更新双重兜底（3.1/3.2） |
| 嵌套锁顺序翻转 → 死锁 | 保留 `账号锁 → 子锁`；保留 `alreadyLocked` 语义（bug_log §36 同锁重入死锁教训） |
| leader 切换瞬间双 sweep | 选主 + 共享态版本 CAS 幂等，两者都要 |
| 迁移链打断 | 改 schema 前**先停 3001**（HANDOFF B 节 / Windows DLL 文件锁）；11 条 → 12 条；`migrate deploy` + `generate` |
| 切换期数据不一致 | 项目无真实老用户、口径「不留兼容后门/旧链路/开关」→ 建议**停机一次性切换**，不做双写灰度 |
| 不变式被破坏 | 全程复查：每块状态一个 owner key、每处写入一个串行键、WS 上行绝不写状态、个人档唯一写入口 `commitState()` |
| 回归成本 | 现有 25 组 E2E / 15 组 UI 冒烟 / 后端 401 + 前端 133 单测均建立在单进程假设上，需逐组确认是否要扩双实例变体 |

**回滚**：每阶段按既有 Git 规矩建并推 `rollback-YYYYMMDD-<阶段>` tag；DB 侧用**新的前向迁移**修复，不回滚已执行的迁移（SQLite/Postgres 迁移链单向）。

## 7. 验收口径（建议）
