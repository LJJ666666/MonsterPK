**关于「彻底转后端才安全」的语义澄清（回应杰哥原话）**：

1. B 方案下 **Redis 不存任何影响玩家权益的真值**——存档 `Save`/`authority.revision`、`BossDamageEvent`、`BossRewardGrant`、`CoopRewardGrant`、`BadgeGrant`、`AchievementGrant`、`IntentLog`、`User.sessionVersion`、每日上限计数，全部只在 Postgres，靠唯一索引与条件更新裁决（§2.1 给判定标准）。

4. 彻底去掉本地存档是 P5-2，单独排期；本期一次只改一件大事，避免把「去存档」和「换存储」两个高风险变更叠在一起。

## 2. 目标架构与不变式

### 2.1 「真值」与「可重建临时态」判定标准（专家 B 定稿）

> **丢失后若导致 ① 存档/资产不一致、② 次数计数或发奖记录错误、③ 跨重启无法从 Postgres 重建且影响玩家权益 → 真值，必须 Postgres 幂等落库。**
> **若仅让「当前一局 / 一场战斗 / 一批野怪」回到可由服务端内容表重新生成、客户端 resync 或重开即可恢复的初始态 → 可重建临时态，允许 Redis。**

| 归类 | 内容 | 落点 |
|---|---|---|
| **真值** | `Save`（含 `revision`）、`BossDamageEvent`、`BossRewardGrant`、`CoopRewardGrant`、`BadgeGrant`、`AchievementGrant`、`IntentLog`、`User.sessionVersion`、**每日上限计数**、房间 quota 的 `committed` | **Postgres 唯一** |
| **临时态** | `RoomState`（含 held / seenNonces / pvp / coop 中间态）、`WildInstance` / claim、`BattleState`、WS 连接表 | Redis（带 TTL + fencing） |
| **辅助** | 锁租约、leader 租约、幂等键、pub/sub 消息 | Redis（不存真值） |

⚠️ 边界：房间 quota `committed` 属「每日次数计数」= **真值**，不能只做 Redis TTL；`settled + finishQuota + 发奖` 以 DB 事务 / 唯一键为最终裁决。

### 2.2 目标分层

| 层 | 职责 | 关键约束 |
|---|---|---|
| 路由层 | 校验意图、取锁 | 保持 `账号锁 → 子锁` 顺序；`alreadyLocked` 非重入旁路 |
| 状态层 | 共享态读写 | PG 行版本 CAS（房间/存档）；Redis Lua（quota INCR / wild claim 单存储原子） |
| 真值层 | 发奖、计数、存档 | 唯一索引幂等：`BossRewardGrant.grantKey @unique`（:145）、`CoopRewardGrant.grantKey @unique` + `@@unique([roomId,userId])`（:169,:174）、`BossDamageEvent.battleId @unique`（:93）、`IntentLog @@unique([userId,nonce])`（:75） |
| 实时层 | pub/sub + 本地推送 | 两频道；各实例按 connection 的 userId **本地裁剪**；revision 跳号回源 |
| 调度层 | 全局 sweep | 单 leader + fencing + 幂等键；本地心跳只管本进程连接 |

### 2.3 不变式复核（全程每工单复查）

1. 每块状态一个 owner key：个人档 `userId`、战斗 `battleId`、野怪 `areaId`、房间 `roomId`。
2. 每处写入一个串行键；WS 上行绝不写状态；个人档唯一写入口 `commitState()`。
3. 客户端上报一律校验；服务端计算全部随机性/经济/等级/捕获/发奖。
4. **新增硬约束**：CAS 基线只能来自 DB；Redis 不得成为第二真值源。

## 3. 六个耦合点：修正后的实施设计

### 3.1 版本源与 CAS（最高优先，W1→W2）

- **现状证据**：`Save` 无 revision 列、`authority String?`（`schema.prisma:50-63`）；基线 `currentState()` 内存优先（`save.ts:124-126`、`session.ts:64-90`、`revision.ts:39`）；`commitState()` 是 `upsert`（`session.ts:94,110-134`）。
- **修正点**：① 顺序改为「先切 provider + baseline 重置」，不是「第 12 条迁移」；② 409 唯一由 DB `updateMany` 的 `count` 决定；③ 覆盖 create 分支；④ 删内存基线参与判定。
- **目标设计**：
  1. W1：provider→postgresql，归档 11 条 SQLite 迁移、重置 lock，生成**一条 PG 基线 init**，`Save.revision Int @default(0)` 随 init 建列；停机一次性按 PG 方言回填 `COALESCE((authority::jsonb->>'revision')::int, 0)`，**不重编号不 +1**；`authority` 为 null/坏数据给 0。
  2. W2：唯一 +1 源收敛到 DB 列，封掉 `monotonicAuthority` / `advanceAuthority` 两处内存 +1。
  3. `commitState()`：`prisma.save.updateMany({ where:{ userId, revision: baseRev }, data:{ …, revision:{ increment:1 } } })`，`count===0` → 409 `REVISION_CONFLICT`；首档 create 分支并发靠 `userId @unique` 的 P2002 → 409；条件失败**短路**内存 apply 与 `broadcastToUser`。
  4. `checkWriteRevision` 保留为「快速拒绝过期请求」，**不得作为最终裁决**；PG READ COMMITTED 足够。
  5. 内存权威态降级为**只读缓存 + 失效广播**，不参与 CAS。
- **改动文件**：`schema.prisma`（含订正 :2 注释）、`prisma/migrations/`、`lib/revision.ts`、`lib/authority.ts`、`lib/gameSession.ts`、`modules/save.ts`、`modules/session.ts`。
- **验收断言**：双进程并发 PUT 同账号 → 恰好 1 成功 1 返回 409；`revision` 严格 +1 不跳号；全量 `verify --strict` 零回归。

### 3.2 锁（W3，与 W4/W5 可并行开发）

- **现状证据**：`chains: Map`（`slotLock.ts:15`）、key 为裸 `userId` / `room:` / `bossq:` / `mapbossq:` / `rank:settle:`（:18-29、`boss.ts:59`、`mapBoss.ts:156`、`rankSettlement.ts:213`）、无超时链（:39-53）、`alreadyLocked` 旁路（`bossReward.ts:122-127`）。
- **修正点**：key 加前缀；fencing token **不用于存档写**；顺序风险改写为「层级环 + 租约不同步过期」；非重入需显式保留。
- **目标设计**：Redis `SET NX PX` 租约锁，命名空间 `lock:acct:` / `lock:room:` / `lock:bossq:` / `lock:rank:`；`AsyncLocalStorage` 或进程内 Set 记已持锁 key，命中即 bypass 以保留 `alreadyLocked` 语义（`SET NX` 若实现成轮询等待会死锁）；watchdog 续租，TTL 按 `rank:settle` 与 Boss 结算 P99（远大于房间 250ms）设定；**DB 条件更新作最后兜底**，锁失效也不写脏。
- **改动文件**：`lib/slotLock.ts`、6 个调用模块（不改调用顺序）、`modules/bossReward.ts`。
- **验收断言**：`tests/slotLock.test.ts` 不变量保持；新增「去掉锁必失败」确定性单测（§5.3）；嵌套两把锁不死锁。

### 3.3 quota 在途闸（W0 预修 → W6 全面改造）

- **现状证据**：`BossQuotaLedger` 同步 Map（`bossQuota.ts:16-43`）；房间 `holdQuota/finishQuota` 纯内存 `committed`（`roomRegistry.ts:36,40,47,193-211`）；`coopQuotaKey` 截断（`coop.ts:96-97`）；`state.bossQuotaKey`（`game/battle.ts:74,228`）。
- **修正点**：房间 `committed` 必须改 DB 计数；TTL≥30min + 续租；release 需 token 防 ABA；release 分支补齐 8 处。

### 3.4 定时器与选主（W0 拆分 → W4）

- **现状证据**：`realtime.ts:154` 心跳 6 件事（stale 清理、ping、**`sweepSessions`**、**`battles.sweepExpired` + quota.release**、**`wilds.sweep` + `publishWild`**、封号复查）；`:216` 房间 250ms；`room.ts:108-109` 无锁；`tickRoom` 由 REST 读触发（`room.ts:97-105,392`）是**第二推进入口**。
- **修正点**：心跳是混合体，必须拆两段；「选主 + 版本 CAS」**不足**，还需 fencing + 幂等键 + 提交成功才 publish；`pvpSettled/coopSettled` 内存标记提共享 CAS。
- **目标设计**：
  - **本地定时器**（每进程各跑）：`findStale`/terminate/remove/detach、`alive=false`+`ping`；**补 `sessionVersion` 比对**，不匹配即本地 `bye` + close（顶号/封号残留兜底）。
  - **全局 sweep**（仅 leader）：`sweepSessions`、`battles.sweepExpired`+release、`wilds.sweep`、`sweepRooms`。
  - 租约 `lock:sweep:global`（PX ≈ 2×心跳）+ 递增 fencing（过期 leader 写共享态全拒）+ 每次 sweep 前 re-check/续租；幂等键：`idem:room:<roomId>`（`room.revision` 条件更新，tick 与 sweep 共用）、`idem:wild:<areaId>:<epoch>`、`idem:quota:release:<battleId>`、`idem:sweep:sessions|battles:<bucket>`。
  - `sweepRooms` 纳入 `withRoomLock`；`tickRoom` 一并 CAS；`pvpSettled/coopSettled` 提为共享 CAS 条件；所有 publish 改为「共享态提交成功才发」。
- **改动文件**：`modules/realtime.ts`、`modules/room.ts`、`lib/roomRegistry.ts`、`lib/wildRegistry.ts`、`lib/wsRegistry.ts`。
- **验收断言**：双实例跑 5 分钟，野怪每区恒 3 只、房间回合无重复推进、quota 不重复释放；leader kill 后新 leader 接管且无双推进。

### 3.5 广播与顶号（W5）

- **现状证据**：仅 `broadcastAll`（`sessionBus.ts:36`，承载 `wild.state`）+ `broadcastToUser`（:31，承载 `session.state`/`room.state`/`battle.state`）；`broadcastToMany` 全 src 无调用点（死代码）；`publishRoom` 逐 seat 发裁剪视图（`room.ts:82-88`）；`kickUserConnections` 只动本地（`realtime.ts:61-74`、`auth.ts:73`）。
- **修正点**：删「四频道」误映射；room 频道**只发 `roomId`**，裁剪在各实例本地做，绝不把含 `pvp/coop` 的全量 RoomState 塞进 pub/sub（`room.ts:44-48` `FORBIDDEN_ROOM_FIELDS`）；兜底复用现有 revision。
- **目标设计**：
  - 两频道：`all`（野怪快照）+ `user:<userId>`（session/room/battle 快照、bye）；删 `broadcastToMany`。
  - 消息带 `(domain, ownerKey, rev)`；三种 state 已自带单调 revision（`wsProtocol.ts:117,146,171`），接收端维护 lastRev，**跳号或订阅重建即回源拉全量**。
  - **必须兜底**：三种 state 快照。**可丢**：`bye`（REST 403 兜底）、hello/pong/error、重复快照。
  - 补 `wild` / `battle` 回源上行（升 `WS_PROTOCOL_VERSION`）或 REST `GET /api/wild`（`wild.ts:69`）兜底；各实例订阅建立时主动 hydrate 全量。
  - 顶号：`onConnected` 的本地 `takeover`（`wsRegistry.ts:73-85`、`realtime.ts:259`）迁共享连接登记 + 分布式接管；`bye` 带 `sv` 且幂等；**明确 403 与 bye 无序**，前端对两者幂等（同一 `SESSION_REPLACED_CODE`，`account.ts:17`）。
- **改动文件**：`modules/sessionBus.ts`、`lib/wsRegistry.ts`、`modules/realtime.ts`、`modules/auth.ts`、`modules/wild.ts`、`wsProtocol.ts`、前端 WS 客户端。
- **验收断言**：A 实例写入后 B 实例连接收到三种快照；跨实例顶号旧连接收到 `bye`；订阅闪断后跳号自动回源；room 消息不含隐藏态。

### 3.6 房间 / 野怪状态机同步→异步（W6 / W7，最大）

- **现状证据**：`RoomStorage` 七方法全同步、`get()` 返回同一对象引用（`roomRegistry.ts:26-49`）；**约 17 处**依赖「改字段 → `bump()` 里 `set()`」；`room.ts:122-143` 四处 `rooms.get()` 后直接改字段**从不写回**；`sweep()` 遍历快照逐房 tick（:603-611）无锁；`wildRegistry.ts` 的 `claim/release/findByBattle/resolve/list/ensure` 全靠全局遍历。
- **修正点**：CAS 定 **PG 行版本 + 事务**（不用 Redis Lua，跨不过 Postgres 且会造第二套版本状态机）；Lua 只用于 quota INCR 与 wild claim 这类单存储原子操作；序列化 3 障碍显式修。
- **房间目标设计**：
  1. `RoomStorage` 改 async + 显式 `load / modify / commit`，事务内 `UPDATE … WHERE revision=?`；**room + quota + 结算写档 + 发奖同一事务边界**。
  2. 序列化修复：`create()` 初始化 `pvpSettled=false`（当前只设 `coopSettled`，:270）；`pvpSettled/coopSettled` 置位/回滚显式写回（`room.ts:125,129,140,143`）；`contributions: Record<number,number>` 反序列化后 key 变 string，统一转 number；optional 字段丢失后的 `===undefined` 判定改用显式布尔。
  3. 保留按接收者裁剪视图（`roomRegistry.ts:157-184`），与 3.5 的本地裁剪串起来。
  4. 区分 `RoomState.revision`（`roomTypes.ts:98-99`）与 `Save.revision`（3.1），两者不是一回事。
- **野怪目标设计**：全量 Redis key —— `wild:inst:<id>` / `wild:area:<areaId>`（3 固定槽）/ `wild:user:<userId>`（在途）/ `wild:battle:<battleId>` / `wild:rev:<areaId>` / `wild:areas` / `wild:spec:<areaId>`；`claim` 用 Lua 一次完成「判状态 + 判同账号在途 + 置 claimed + 写两索引」；`spawn/ensure` 与 claim 同脚本或区域锁，防两 sweep 并发各补 1 只超 `WILD_PER_AREA=3`；**超时归还由 leader sweep 用 Lua 原子「清过期 + claimed→available + 删在途键 + 补到 3 只」**，不是靠 key TTL 自动删。
- **改动文件**：`lib/roomRegistry.ts`（约 600 行状态机重写）、`lib/roomTypes.ts`、`modules/room.ts` / `coop.ts` / `pvp.ts`、`lib/wildRegistry.ts`、`modules/wild.ts`。
- **验收断言**：同房间双意图只推进 1 回合、`CoopRewardGrant` 只 1 行；同 `wildId` 双 claim 只 1 成功；超时归还后每区恒 3 只；`pvpSettled` 幂等标记跨实例不丢。

## 4. 工作顺序（工单，tx 排定，不可跳步）

### 4.1 排序原则

1. **W0 先做**：全部是「零行为变更的接口抽象 + 单实例可修的小 bug」，不需要任何外部资源，把后续切换的改动面收窄，且能立刻用现有 47 阶段 verify 验收。
2. **provider 切换必须早于任何 schema 改动**：否则「第 12 条 SQLite 迁移」是白做（§1#1）。
3. **CAS 与锁早于一切共享态写入**：W2/W3 不给串行保证，后面每个状态机都没有正确性基础。
4. **选主与广播早于房间/野怪**：W4/W5 不做，W6 的推进会重复且状态推不到对端。
5. **W6 与 W7 可并行开发**（共用同一套锁/CAS 语义），但必须**同一批验收**，避免两套语义各写各的。
6. **W8 允许按 `userId` 粘性路由先降级**，降低一次性风险。
7. 每个工单独立 `rollback-YYYYMMDD-<工单>` tag；涉及 schema 的工单**先停 3001**（HANDOFF B 节 / Windows DLL 文件锁）。
