> 用途：联网化改造的任务总表。**先看盘点 → 按优先级实施 → 逐项回填进度**。
> 状态口径：⬜ 待办 / 🔨 进行中 / ✅ 已完成 / ⏸ 暂停

> **北极星方向（2026-11-04 修正）**：最终形态为**服务端权威 + 实时多人同玩**——WebSocket 实时传输，战斗 / 捕获 / 经济由服务端结算，客户端只发意图、收状态、负责渲染。本地存档是**过渡态**：待服务端权威 + 实时就绪后（P3 / P5）再去除，届时仅保留登录态 / 设置等本地非游戏状态。
> 因此后续优先级从「先玩法 / 榜单」调整为**「先夯服务端权威与实时地基，再上多人玩法」**。原 P0-3 的 localStorage 自动同步是到 P3 前的桥接方案，P3 客户端变瘦终端后即退役。

### 1.3 关键缺口（决定优先级，按新方向重排）

1. ~~**服务端对存档不透明且不可信**~~ → **已闭环（P1-1 / P1-1b）**：`data` 现做结构 + 数值契约校验与风控分级，越界改档会 403 封号并强制登出；但**合法区间内的数值微调仍看不出来**，需 P1-2 / P3 根治。
2. ~~**关键随机与结算仍在客户端**~~ → **已闭环（P1-2，2026-11-06）**：捕获 RNG、战斗奖励、商店价格/扣款、挂机时钟与掉落全部上移服务端；客户端发意图带 nonce，服务端裁决后由 `PUT /api/save` 精确核对增量；整包自动 PUT 的冲突用「权威摘要 + 意图授权」解决（见 §七）。**残留边界**：GG 修改器改内存、加速器改节奏、战斗中间态（HP/PP）伪造仍需 P3 瘦终端根治。
3. ~~**无实时传输层**~~ → **通道已打通（P2-1，2026-11-06）**：`ws://…/ws` 已完成鉴权、心跳、重连与限流；**但仍无在线权威态**，游戏状态依旧走整包存档 + 意图裁决，须 P2-2 `GameSession` 才能支撑同屏 / 共野 / 实时对战。
4. **JWT 无 `exp`**（已修于 P0-4）、**存档版本口径脱钩**（已修于 P0-1）——属已闭环项，列入仅作追溯。
5. **无任何多人能力**：排行榜、对战、交易、成就统计都未做，且现有架构下榜单 / 成就应由服务端状态派生而非客户端上报。
6. ~~**游戏内遗留缺口**~~ → **已闭环（P1-3，2026-11-06）**：进化石、`amulet_coin`、`exp_share`、捕获率稀有度/等级差均已修复。**内容缺口**：40 只幻兽里仅 `spark_mouse` 配了 `stone_thunder` 道具进化，其余三种进化石暂无目标（内容表待补，非代码缺陷）。

## 二、优先级排序（按北极星方向重排）

排序原则：**先修服务端权威与可信（防作弊地基）→ 再建实时传输 → 再把模拟上移服务端 → 最后上多人玩法与上线**。任何让服务端「相信」客户端数据的任务，都必须等数值校验（P1-1）落地，否则等于给作弊开绿灯。

| 序 | 任务 | 状态 |
|---|---|---|
| P0-1 | 统一存档版本与迁移口径 | ✅ |
| P0-2 | 后端存档结构校验 + 冲突元数据 | ✅ |
| P0-3 | 自动云同步（过渡桥接，P3 后退役） | ✅ |
| P0-4 | 登录态健壮性（JWT exp + 401 统一登出） | ✅ |
| P0-5 | 移除手动备份 UI | ✅ |

### P1 — 服务端权威基础（防作弊 + 实时化前提）← 当前重心

| 序 | 任务 | 为什么排这里 | 依赖 | 验收口径 |
|---|---|---|---|---|
| P1-1 | 服务端存档数值校验 | 现在服务端只认结构不认数值，客户端可任意改档；这是「防改档」硬门槛，也是后续实时化的信任根 | P0-2 | 服务端解析 `data`，校验金钱/等级/捕获数/进化链等数值合理性与版本一致；非法存档拒绝并告警；写单测覆盖典型作弊档 |

| 攻击手段 | P1-1b 现状 | 根治层 | 根治机制 |

| 填未来时间戳永远覆盖云端 / 刷挂机 | ✅ 服务端钳制，不生效、不封号 | P1-1b（往前调） | `serverClock.ts` 覆写为服务器时间 |

> 才是杰哥要的「他人各种修改都拦下来」。这也是把 P1-2 排为下一步的原因。

### 6.3 误封防线与运维

- `antiCheat.ts` 采用**改档特征白名单**：格式错误、旧版存档、版本错配一律只 `400`，**绝不封号**。
- 每次封号在同一事务写 `BanRecord`（违规码 / 原因 / 存档摘要 / 时间）与 `User.bannedAt`，可审计。
- 管理员授权：`npm run admin -- grant <用户名>`（写库）或 `.env` 的 `ADMIN_USERNAMES`；
  **绝不写死固定用户名**，否则公网谁注册这个名字谁就是管理员。
- 解封：`npm run admin -- unban <用户名>`；查记录：`npm run admin -- audit <用户名>`。
- 前端 `useIsAdmin()` 只是 UI 收敛（隐藏测试菜单），**不是安全边界**；后端一律重新判定身份。

### 6.4 已同步到 P1-2 / P3-1 的追加验收口径

- **P1-2**：捕获成功与否、金币/道具/挂机结算全部服务端裁决；`startedAt`/冷却/收益 delta 以服务端时钟为准，
  改系统时间（往前或往后）均不产生额外资源且**不封号**；关键 RNG 在服务端、结果不可伪造；
  意图请求带 nonce / 幂等键防重放；端到端含「改时间不生效」用例。
- **P3-1**：客户端只发意图、服务端结算并广播；`rules.ts`/`idle.ts`/`gen.ts` 服务端化；
  **GG 修改器改内存无效**、**加速器改节奏无效**；配合 P3-2 瘦终端后，P5-2 才安全去除本地存档持久化。

## 七、P1-2 实施拆解与待拍板决策（2026-11-06 新增）

### 7.1 必须先解决的架构冲突：整包 PUT 会覆盖服务端裁决

现状 `startAutoSync()` 订阅 `useGameStore` 三槽位变更 → 1.5s 防抖 **整包 PUT `/api/save`**。若只在服务端加裁决接口而不改这条链路，客户端仍会按自己算的结果改本地 store，下一次自动 PUT 就把客户端结果覆盖回数据库，**服务端裁决形同虚设**。P1-1 的数值校验只查范围，判断不了「这个 delta 是不是服务端发的」。

| 路线 | 做法 | 评价 |
|---|---|---|
| **A（推荐，渐进）** | 关键路径改为「发意图 → 等服务端裁决 → 应用服务端返回的权威存档」；同时给 `PUT /api/save` 加**权威摘要比对**（服务端维护 money / party / inventory / idle 等裁决字段的期望值，客户端自造 delta 一律拒绝）；整包存档暂时保留为过渡载体 | 改动集中在 4 个写入点 + `sync.ts` + 后端新模块，不碰实时架构，符合「每步测通再下一步」 |
| B（激进） | 直接上 `GameSession` + 瘦终端、去掉整包 PUT | 等同把 P3 前置，且 P2 WebSocket 未做，工作量大、缺陷耦合，不推荐 |

### 7.2 分步拆解（每步测通再下一步）

| 步 | 内容 | 涉及代码 | 验收口径 |
|---|---|---|---|
| **P1-2-a** | 挂机：`POST /api/idle/start\|claim`，服务端自己记 `startedAt`、按服务端时钟算 delta、发放金币/捕获器 | `useGameStore.ts:614~653` `src/game/idle.ts` + 后端新模块 | 客户端把系统时间往前/往后调均不产生额外资源且**不封号**；重复 claim 只发一次（nonce / 幂等键）；E2E 含「改时间不生效」用例 |
| **P1-2-b** | 捕获 RNG 上移：服务端掷骰并回写结果，客户端不再决定成败 | `useGameStore.ts:394~424` `rules.ts::attemptCapture` | 意图请求带 nonce；客户端伪造「捕获成功」无效；结果由服务端下发 |

### 7.3 杰哥拍板与实施结果（2026-11-06）

| 决策项 | 拍板 | 落地 |
|---|---|---|
| 范围 | **a~d 全做** | 四步全部完成，逐步测通 |

| 并行 | **P1-3 合适则并行** | 判定为**不能真并行**（捕获率撞 b、金币翻倍/经验分享撞 c、进化石撞 store 写入），改为把三项拆开嵌入对应步骤一起做，避免返工 |
| 存档 | 31 项未提交 | 杰哥确认「只是测试、数据没了就没了」，**未建 commit**；所有改动仍在工作树，外部推送仍需另行确认 |

**路线 A 的最终机制**（比 7.1 的初稿更严密）：
1. `POST /api/actions/:type` 收到意图后：消费一次性 nonce（失败也消费，防反复重试刷 RNG）→ 用既有三层风控校验请求携带的「当前存档」→ 单调比对后把它落库为**可信基线** → 服务端掷 RNG / 用服务端时钟 / 查服务端价格表 → 登记 `authority.pending`（含基线摘要与允许的精确增量）。
2. 客户端按裁决结果改本地 store，随后 `commitIntent()` 取消防抖、**立即** `PUT /api/save` 并带 `intentNonce`。
3. 服务端按 pending 精确核对「相对基线的资源增量」：多一分少一分都 400（不封号，避免网络竞态误伤）；通过后抬升权威摘要、清除 pending。
4. 不带 nonce 的普通整包 PUT 只做单调比对（资源不得更富），放行后把合法消耗同步进摘要；因此旧的自动同步不会覆盖服务端裁决。
5. 新建/重置存档用 `rebase` 标记 + 服务端「新档特征」校验重建基线（伪造 rebase 最多只能拿到初始资源，无收益）；管理员测试菜单走 `admin_test` 意图，由服务端判定身份后授权重建基线。

> **契约变化**（务必知悉）：P1-2 起客户端**不能**再用整包 PUT 自行把资源改高；旧 E2E 里「同一账号连续写不同资源档」的用例已改为独立账号首次写档建立基线，全部安全断言（400 / 403 封号 / 审计 / 时间钳制）保持原样，57 例仍全绿。
> **残留边界**：GG 修改器改客户端内存、加速器改节奏、战斗中间态（HP/PP/状态）伪造，仍需 P3 服务端模拟 + 瘦终端根治；`captureRate` 的 ID 真值校验也留到服务端持有完整内容表的 P3。
